# TypeBridge × Lombok integration experiment

This directory is an isolated compiler experiment for `ApiGeneratorManager`.
It does **not** change generated APIs or production modules.

## Question

Can a TypeBridge-style javac elaboration see a method generated by the exact
Lombok version used by this repository (`1.18.42`) and rewrite an otherwise
invalid strong-type call before javac rejects it?

The fixture deliberately contains:

```java
@Builder
class Order {
    CustomerId customerId;
}

return Order.builder().customerId(rawUuid).build();
```

Normal Java + Lombok must reject the call because `customerId(...)` expects
`CustomerId`, not `UUID`.

The probe waits until annotation processing is complete, verifies that Lombok's
`Order.OrderBuilder.customerId(CustomerId)` member is visible, and elaborates the
argument to `new CustomerId(rawUuid)` before normal attribution.

## Safety of the experiment

- isolated under `experiments/`;
- no production Maven module is modified;
- generated output behavior is unchanged;
- negative control proves the source does not compile without the compiler probe;
- runtime output is checked after successful elaboration;
- the probe is intentionally narrow and is **not** presented as the full TypeBridge engine.

## Run

Requires JDK 21+ because the current TypeBridge compiler prototype targets javac
21–25. ApiGeneratorManager's GitHub Actions backend job already runs on JDK 21.

```bash
bash experiments/typebridge-lombok/run.sh
```

A successful run proves the Lombok/compiler timing assumption needed before
integrating the full TypeBridge engine into generated strong-type APIs.
